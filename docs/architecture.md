# Code architecture for the VM

> Status: current implementation boundaries and remaining specification work.

`spec.md` is the source of truth. Its **Decisions** section overrides older prose, examples, prototypes, and existing code. This document describes how to implement that specification; it does not define VM semantics.

## Scope and dependency direction

```text
docs/spec.md (machine behavior and decisions)
       ↓
Lua ISA definitions + instruction semantics + cache-state model
       ↓
generated C interpreter handlers + register-addressed JIT stencils
       ↓
C module loader/verifier + standalone ABC-to-ABC `abc-opt` + configured eager/lazy residualizer
       ↓
host-selected interpreted, eager-JIT or lazy-JIT mode, embedding API
```

This work builds a VM whose **implementation is C generated by Lua**. Portable C emitted from verified bytecode is a separate build-time product and peer symbolic sink, not the run-time native JIT and not a Let-specific backend. No Let frontend detail is an instruction semantic.


`gen/banked.lua` emits cache-state-specific concrete interpreter handlers. `gen/symbolic.lua` emits the musttail symbolic handlers used by every optimizing backend, and `gen/stencils.lua` emits register-addressed operation stencils plus the stable lazy-entry stencil. `src/symbolic.c` owns shared abstract A/B/C execution, folding, continuations and structured exits. Three peer sinks consume it: native `src/residualize.c` performs placement in the symbolic stack cache and copies stencils directly; `src/optimize.c` records only the ordered DAG needed for canonical ABC re-projection; and `src/residual_builder.c` records the explicit semantic values and blocks needed by strict structured C. Native code is never lowered through either residual representation. Profile-5 loading/execution, Whippet/Nofl integration, ordered maps/layout tokens, managed storage, dynamic calls and canonical optimization are implemented. Portable C implements integer/control/direct-call residue; float, memory, indirect/foreign, managed and dynamic C lowering remain alongside keyed/method source semantics, dynamic quickening caches, escape-based wide-integer lowering and lazy tag/token propagation.

## Ownership rules

- **Spec → ISA:** Opcode numbering, lengths, operands, stack effects, aborts, call/frame rules, and site-version rules follow `spec.md`. The generator must not silently invent or change them. The loader rejects internal opcodes in input modules.
- **ISA → verifier and runtime:** The same instruction definitions supply generated opcode metadata and interpreter emission. Verification checks instruction boundaries (including variable-length `SWITCH` and `EXT` forms), every `JMP32`/`SWITCH` target, integer/address/float kinds, stack shapes, frame layouts, call signatures, valid control-flow joins, descriptor-root traversal, and the transitive `allocation-free` fact before execution. Float arithmetic and ordered branches use IEEE-754 binary64 cell bits; checked float-to-integer conversions report abort reason 3, and integer-to-float conversion implements ties-to-even independently of ambient host rounding. The generator may rely only on verified invariants.
- **Semantics versus placement:** `semantics.lua` describes changes to A, B, C, instruction pointer, memory, and observable errors. `cache.lua` maps those changes onto physical register and spill locations; cache placement is not part of the VM's public ABI (Decision 1).
- **Interpreter cache and quickening:** A and B share four anchored registers; C has its own bank. Every executable opcode has generated cache-state handling and direct `musttail` dispatch; there is no generic synchronized fallback. Fixed-length handlers advance `ip` by their literal encoded length. A measured monomorphic dynamic site may replace `EXT` in its private code copy with a same-total-length operation-specific internal opcode; unquickened and polymorphic sites keep selector dispatch, and all internal forms reject in serialized code. Profile 5 must reclaim opcode space from prototype call quickening before assigning these forms. Dynamic binary operators use A0/B0 and `.X` like typed operators. Calls and returns carry cache state; `CALLOC` flushes C, while `FCALL` performs full C-ABI synchronization.
- **Compiled-tier input:** The same semantic definitions used for interpreter handlers feed the JIT's register-addressed stencil generator. The interpreter keeps state-keyed handlers; the JIT uses register-addressed stencils. Offline tooling compiles and extracts stencils; no C compiler runs when a module is loaded or executed.
- **Compile-time execution:** The Let compiler lowers fully known user subprograms to temporary verified modules and runs them in an `abc_vm`; it does not reimplement executable language semantics in Lua. The compiler independently configures interpreted, eager or lazy policy for staging modules. `FCALL` remains disabled. No instruction/fuel or logical-work budget exists: execution continues until completion, language abort, actual resource failure or external interruption. The compiler supplies delayed progress and Ctrl-C static-stack diagnostics. Speculative folds use disposable/checkpointed images, accepted module initialization supplies a copied residual image, and compile-time VM-local addresses never enter serialized output.
- **Dynamic runtime and source ownership split:** Generated helpers own `any` tags, canonical nonallocating float encoding, boxing/unboxing and generic arithmetic. Handwritten runtime code integrates vendored Whippet `stack_conservative_mmc`/Nofl, pins every published object to preserve plain-address identity, supplies conservative native/VM-stack ranges and descriptor-precise heap/module tracing, and owns object headers, each open word's collected ordered hash map, and process-wide non-reused numeric layout-token allocation. A token owns no key metadata. Structural mutation changes it; value replacement does not. Constant-key caches guard `(token, key, slot)`, while computed keys use generic lookup. Managed strings retain owners; SLet/foreign views copy. An SLet producer emits stack-disciplined borrows and no managed roots; Let uses profile-5 promotion and trace descriptors where managed values occur. The VM enforces capabilities without inspecting filenames.
- **Compilation by configuration:** After verification, interpreted mode uses generated handlers only. Eager mode creates all reachable capped block versions at load and emits generic checked code for unavailable facts. Lazy mode retains persistent version state and stable stubs; first arrival creates a version from checked context, including tags and layout tokens when present. Tokens are scalar generations and retain no word/map storage. At the cap, conform to the most specific compatible version, ultimately generic. Both JIT policies share partial evaluation, stencils and virtual continuations.
- **Emission, calls and timing:** `src/residualize.c` owns symbolic propagation, versions, stencil copying, relocations and executable-code mappings. No C compiler runs at load or first arrival. Every known acyclic direct call uses a virtual continuation while the callee entry has room under the ordinary version cap; there is no byte-size or nesting-depth heuristic. At the cap, a direct call stores a native resume address in the VM C-stack return cell and jumps to the callee. Recursive SCCs use the same mechanism as cyclic CFGs: arguments conform to shared capped register-entry versions, live activation state is materialized, and single-cell results return in a canonical register before `RET` restores stack bases and jumps through the run-time continuation. Tail recursion stays a direct backedge. Only host, foreign and explicit runtime-helper boundaries use the host C ABI. Residualized code keeps a checked wide integer as raw register bits across compatible edges and materializes its dynamic box only at an escape. Eager mode completes reachable load-time compilation before execution. Lazy mode enters the compiler only through stable first-context stubs, then publishes and reuses the version. There is no fuel accounting, tracing, hotness counter, heat-driven tier switch or source-extension test. Safepoints are determined by generic/allocating bytecode; a host request can remain pending across a verifier-proven allocation-free loop.
- **Site versions:** The interpreter keeps VM-private call/return and dynamic-site quickening. Eager targets patch at load; lazy targets use stable stubs. Each indirect-call or generic site owns one knowledge state shared by all arrival-context versions. Site patches move monotonically from observing to checked-specific and then permanent generic after mismatch. A passed tag or layout-token check can become downstream context. No execution counters or heat-driven respecialization exist.
- **Handwritten C:** Owns module/VM lifetime, image storage, host ABI, limits, configured modes, persistent lazy state, stable stubs, foreign bindings, collected open-word maps, layout-token generation, heap ownership, GC integration and cold helpers. It must not grow competing arithmetic or tag semantics. Generated semantics own interpreter handlers, generic-value helpers, foreign bridges and offline stencil sources.
- **Build:** The Makefile regenerates C and headers from Lua inputs, compiles and extracts the stencils offline, then compiles the runtime; generated output stays under `build/`, is never hand-edited, and can be reproduced after `make clean`.

## Validation

Required validation covers instruction/cache transitions, same-length `EXT` quickening, A0/B0 routing, local block-version generalization and three-policy agreement. Dynamic validation also covers canonical floats, escape-only wide-integer materialization, O(live fields) open-word map storage after thousands of keys and structural churn, non-owning/non-reused layout tokens, cached-slot invalidation on structural mutation, missing-result aborts, allocation-free facts and pending collection requests. Lazy validation checks first-arrival creation/reuse and locally limited tag/token contexts. The complete obligations remain in `dynamic-profile.md`; current validation covers ordered-map growth/removal, direct/captured and partial/saturated calls, aggregate and managed storage boxing, and forced Whippet collection through module and managed-interior roots, while quickening, cache and lazy-fact suites remain in progress.
